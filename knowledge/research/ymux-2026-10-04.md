# ymux-2026-10-04 — research report

## Question

The FOLLOWUPS P2 entry for 2026-10-04 (FOLLOWUPS.md:20, "macOS local tmux pane not smoke-tested after Phase 98") asks for a hands-on smoke test on a Mac. In a local tmux pane, the wheel at a shell prompt should scroll 3 lines per notch and keep the `[N/M]` counter pinned. Scrolling past the bottom should type nothing. `tmux show -g assume-paste-time` should print 0. Trackpad scrolling should be proportional, with no runaway. A RESEARCH stage cannot drive a Mac, so this report does the static half of the job. For each outcome it traces the code path a macOS local pane takes, predicts what the smoke test will show, and names the risks that would make it fail. The live observation itself stays open; see `## Open questions`. Every claim was checked against the tree at `6ca7e76`.

### O1 — [WHEN] user scrolls wheel at shell prompt in local tmux pane → [SHALL] 3 lines scroll per notch with `[N/M]` counter pinned
### O2 — [WHEN] user scrolls past bottom of buffer → [SHALL] no characters are typed into the shell
### O3 — [WHEN] user uses trackpad scroll → [SHALL] motion is proportional with no runaway acceleration
### O4 — [SHALL] `tmux show -g assume-paste-time` outputs 0, confirming Phase 98 configuration applied

## Findings

### Shared path: how a macOS local pane reaches Phase 98

- **The pane is tmux-backed and the wheel proxy gets armed.** On non-Windows targets, `spawn_local_pty` types a tmux attach-or-create script into the login shell 900 ms after spawn (`app/src-tauri/src/lib.rs:3007-3049`). The `LocalSession` it stores carries `tmux_session: persist_session.clone()` (`lib.rs:2954`). `pane_persistence_list` lists every Local session that has a `tmux_session` (`lib.rs:11308-11327`). App.tsx arms the wheel proxy from exactly that map: `ti.setTmuxScroll(!!m?.[pid])` (`app/src/App.tsx:903`). So on a Mac the proxy is armed through the same mechanism as Windows/zellij and SSH. Nothing in this path is platform-gated.
- **The proxy itself is platform-neutral.** `attachCustomWheelEventHandler` hands the event back to xterm unless all of these hold: the proxy is armed, no Shift/Ctrl is held, the buffer is `alternate`, and mouse tracking is `none`. Otherwise it sends `wheelSteps(...).steps` copies of `\x1b[1;2A` or `\x1b[1;2B` (`app/src/terminalInstance.ts:1045-1062`). There is no `cfg`/platform branch in this code.
- **Which conf is loaded depends on the Mac's disk, not on the build.** The attach passes `-f $HOME/.ymux/tmux.conf` and chains `source-file -q $HOME/.ymux/tmux.conf` only when `use_ymux_tmux_config` is on AND `~/.ymux/tmux.conf` exists (`lib.rs:3014-3020`, `lib.rs:3457-3471`). `local_tmux_conf_ready()` checks existence only, not content (`app/src-tauri/src/local_setup.rs:1156-1159`).
- **Critical: nothing refreshes a Mac's local conf on upgrade.** The only writer of `~/.ymux/tmux.conf` on a Mac is `deploy_tmux_conf_local()` (`local_setup.rs:1202-1220`). It is reachable only as the `DeployTmuxConfLocal` step of the setup wizard's mac chain (`local_setup.rs:1577`, `app/src/LocalSetupFlow.tsx:67`, `:191`). Phase 98 fixed the conf refresh for **remote** hosts: "Bootstrap now ensures the conf on the CLI-hash-matches path too" (commit `0574645` message; its stat touches `crates/ymux-bootstrap/src/lib.rs` and not `local_setup.rs`). The local macOS path was not changed. A Mac whose wizard ran before Phase 98 therefore keeps its pre-98 conf, and the attach re-sources that **stale** file every time. The wizard can report this: it shows `conf ✗` when the file is not byte-identical to the bundled conf (`LocalSetupFlow.tsx:268`, `local_setup.rs:1189-1196`). Re-running the wizard redeploys the conf, because the step is skipped only when `tmux_conf_ok` (`LocalSetupFlow.tsx:191`).

### O1

**Answer:** If `~/.ymux/tmux.conf` matches the bundled Phase 98 conf, one mouse notch should scroll exactly 3 lines in one tmux operation, with the counter pinned. That holds only if WKWebView reports a notch as ≥ 50 px of `deltaY`, which is unverified. On a Mac with a stale conf, O1 is expected to fail the same way Windows did before Phase 98.

**Evidence:**
- Conf: on the main screen, `S-Up` → `copy-mode -e; send-keys -X -N 3 scroll-up`. Inside copy-mode, `S-Up`/`S-Down` → `send-keys -X -N 3 scroll-up|down` in both mode tables (`app/src-tauri/resources/ymux-tmux.conf:120-125`). That gives 3 lines per key as one operation. The PROGRESS Phase 98 entry says one-op scrolling is what keeps the counter pinned ("counter scrolls with the text" was the bug; PROGRESS.txt:7810).
- Proxy: one key per notch-class event. `wheelSteps` returns ≥1 step only when the accumulated magnitude is ≥ `MIN_NOTCH_PX` = 50 px (`app/src/wheelSteps.ts:18-19`, `:49-50`). `NOTCH_PX = 100` is documented as tuned for "Chromium/WebView2" (`wheelSteps.ts:15-17`). On macOS, Tauri renders in WKWebView, not WebView2.
- **Risk (unverified):** Apple's wheel deltas are accelerated, and macOS exposes no notch count (Chromium code review 2461323002, retrieved 2026-10-06). If a slow single notch reports < 50 px in WKWebView, it lands in `carry` and scrolls nothing. Two slow notches would then scroll 3 lines, not 6. A fast notch could map to 2+ steps (`Math.round(mag / NOTCH_PX)`, `wheelSteps.ts:50`), giving 6+ lines. Either result breaks "3 lines per notch" without being a tmux bug.

**Confidence:** medium for the conf side (tmux 3.4 harness, PROGRESS.txt:7810: "6-in-a-packet = 18 lines"). Low for the WKWebView delta calibration. It goes up once the live test records the observed lines-per-notch for one slow notch and one fast notch.

### O2

**Answer:** With the Phase 98 conf loaded, scrolling past the bottom should type nothing. With a stale pre-98 conf, the 1 ms paste detection is back, and a fast scroll down past the bottom can type `^[[1;2B` into the shell.

**Evidence:**
- `set -g assume-paste-time 0` (`ymux-tmux.conf:138`). The rationale: with paste detection on, burst keys skip their bindings, and "once `-e` had left copy-mode the rest reached the program as raw `^[[1;2B`" (`ymux-tmux.conf:127-137`).
- Outside copy-mode on the main screen, `S-Down` is bound to an empty command (`ymux-tmux.conf:121`). A key that *does* hit its binding is therefore swallowed, not typed. The leak happens only when the binding is skipped, which is the paste-detection path.
- Reproduced on real tmux 3.4 before and after the fix (PROGRESS.txt:7810). Verified live on Windows build 37154900591 (PROGRESS.txt:7820).
- Stale-conf exposure: see the shared path above (`local_setup.rs:1156-1159`, `:1202`, `LocalSetupFlow.tsx:191`).

**Confidence:** high, conditional on the conf being current. Checking O4 first settles that condition.

### O3

**Answer:** The design is proportional. Small trackpad deltas accumulate in `carry` and pay out one key per ~100 px. A reversal drops the carry. Each event is capped at 10 keys. The 91.D "runaway" (3 keys for every tiny event) is gone. macOS momentum (inertial) events are not told apart from finger-down events, so a flick keeps scrolling after the fingers lift. That is native-feeling inertia, not runaway, but the live tester should know to expect it.

**Evidence:**
- Carry and payout: `wheelSteps.ts:41-55`. Reversal reset: `wheelSteps.ts:46`. Per-event cap `MAX_STEPS = 10`: `wheelSteps.ts:23`, `:50`. Carry kept between events: `terminalInstance.ts:1056-1057`.
- Unit tests: `app/src/wheelSteps.test.ts` (added in `0574645`; it runs in CI under `npm test`, not run here per Rule #17).
- Nothing in the handler checks the momentum phase (`terminalInstance.ts:1045-1062`).

**Confidence:** medium. The logic is pure and tested. How it feels on a Mac trackpad, whose deltas come from WebKit and not Chromium, has not been observed.

### O4

**Answer:** It prints `assume-paste-time 0` only if the tmux server has sourced a Phase 98 conf. On a Mac that ran the setup wizard before Phase 98, or that never ran it, expect `assume-paste-time 1` (tmux's default) until the wizard's "Deploy the tmux configuration" step runs again.

**Evidence:**
- The line is present in the bundled conf (`ymux-tmux.conf:138`) and pinned by the conf lint (`lib.rs:13716`).
- Server-side adoption: every attach chains `source-file -q $HOME/.ymux/tmux.conf`, so a running server picks up whatever file is on disk (`lib.rs:3457-3462`).
- The file on disk is written only by the wizard (`local_setup.rs:1202`, `:1577`). No startup or upgrade path refreshes it (grep for `deploy_tmux_conf_local|DeployTmuxConfLocal` finds only the wizard plumbing: `local_setup.rs:1577`, `:1621`, `LocalSetupFlow.tsx:67`, `:191`).
- If the setting is off or the file is missing, `-f` is not passed and the user's own `~/.tmux.conf` applies (`lib.rs:3014-3020`). O4 then fails by design.

**Confidence:** high for the mechanism. Which state any particular Mac is in is unknown.

## Recommendation

Do not close the P2 entry from this report. It still needs a real Mac, which only Yossi or a collaborator has. Run the smoke test in this order:

1. **Bring the conf current first.** Open the setup wizard and confirm it shows `conf ✓`. If it shows `conf ✗`, re-run it so `DeployTmuxConfLocal` writes the Phase 98 conf. Then open a new local tmux pane, which re-sources the conf on attach.
2. Check O4 (`tmux show -g assume-paste-time` → `assume-paste-time 0`).
3. Run O1 and O2 with a real notched mouse. Record the lines per **single slow** notch: 0 lines would mean WKWebView reports < 50 px per notch, a `wheelSteps.ts:18-19` calibration issue. Then run O3 on the trackpad.

The trade-off: this treats a Mac with a stale conf as a setup step rather than a bug. Phase 98 did not add an automatic local refresh. A follow-up should consider one: re-deploy when `local_tmux_conf_ok()` is false, at the spawn call site `lib.rs:3014`, mirroring what Phase 98 did for remote bootstrap. If testers routinely hit `assume-paste-time 1`, that follow-up becomes a P1. If a slow notch scrolls 0 lines, a macOS-specific `NOTCH_PX` (or a `deltaMode`/platform check) at `wheelSteps.ts:18` is the fix site.
