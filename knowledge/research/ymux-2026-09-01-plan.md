# ymux-2026-09-01-plan — research report

## Question

What would it take to ship a `ymux-brief` skill in the ymux skills registry? That covers how the existing installer (`skills.rs`) and UI (`YmuxToolsTab`) use the registry, how a file can be bundled with the Tauri app and found at runtime, where startup seeding would go so the skill is written once without overwriting a user's edits, and what the SKILL.md must teach about the `[ymux-brief]` block. This is research only. No code changes.

### Q1 — Why does the skills registry ship empty — which code path reads the registry and what populates it
### Q2 — What does the installer in `skills.rs` copy, from where, and what does YmuxToolsTab render
### Q3 — What must change in the Tauri config and build to bundle a SKILL.md as a resource, and how the desktop app resolves that resource at runtime
### Q4 — Where would startup seeding hook in so the skill is written once on first run without overwriting a user-edited copy
### Q5 — What the `[ymux-brief]` block format requires the SKILL.md to teach, per docs/BRIEF.md

## Findings

### Q1

**Answer.** The registry is empty because nothing writes to it. The only code that reads it is `skills_list` / `skill_install` in `skills.rs`. No code in the repo creates `config_dir()/ymux-tools/skills/`, and no files ship for it. Filling the registry was deliberately left out of scope when the module was written, and the 2026-09-01 BRIEF decision chose a CLAUDE.md snippet over seeding for the same reason.

**Evidence.**
- `app/src-tauri/src/skills.rs:8-9` — module doc: "the source registry itself (populating `ymux-tools/skills/`) is out of scope here."
- `app/src-tauri/src/skills.rs:40-43` — `registry_dir()` = `config_dir_pub()?.join("ymux-tools").join("skills")`. Its doc comment reads "Missing dir ⇒ caller treats as empty."
- `app/src-tauri/src/skills.rs:58-62` — `skills_list` returns `Ok(Vec::new())` when the directory does not exist. On a fresh install it never exists, because `config_dir()` only creates the parent `ymux` directory (`app/src-tauri/crates/ymux-core/src/lib.rs:58-70`, `:96`).
- `git grep -n "ymux-tools"` → the only Rust code that touches `ymux-tools/skills` is `skills.rs`. The other hits are the chrome Ticker / statuslines (`lib.rs:170,243,629,3127`, `rpc_server.rs:1379`, `cli/src/hooks.rs:138`) and the registration comment `lib.rs:13093`.
- The repo's `ymux-tools/` tree holds only `README.md` and `statuslines/` (`ls -R ymux-tools`). There is no `skills/` folder to copy from.
- `docs/vault/backend-panes.md:237-240` — "Populating the source registry is out of scope for this module."
- `docs/DECISIONS.md:817` — "adoption via a copy-paste CLAUDE.md snippet … not a seeded skill (the skills registry ships empty and seeding is new plumbing)".
- `git log --oneline -- app/src-tauri/src/skills.rs` → introduced in `bc505d2f feat(skills): winmux-tools skills registry backend (Half B)`, then the rename `90626bb1`. Seeding was never added after that.

**Confidence:** high.

### Q2

**Answer.** `skill_install(workspace_id, name)` copies the whole folder `config_dir()/ymux-tools/skills/<name>/` recursively:
- **Local workspace:** to `~/.claude/skills/<name>/` with `std::fs::copy`. Symlinks are skipped, existing files are overwritten, and stale extra files are left in place.
- **Remote workspace:** to `$HOME/.claude/skills/<name>/` over SFTP through the workspace's live SSH handle, after a `mkdir -p` for every directory needed.

`YmuxToolsTab` lists the registry with `skills_list`, showing name and top-level file count. It marks entries already found in `~/.claude/skills/` with `skills_installed`, and offers Install, or Reinstall + Uninstall for an installed entry. When the list is empty it shows "No skills in the registry yet — drop a skill folder into ymux-tools/skills/."

**Evidence.**
- `app/src-tauri/src/skills.rs:30-38` — `valid_skill_name`: only `[A-Za-z0-9._-]`, at most 128 chars, and not `.` or `..`. So `ymux-brief` is a valid name; the unit test at `:264-269` accepts the similar `pdf-tools`.
- `app/src-tauri/src/skills.rs:19-25` — `SkillInfo { name, files }`, exported through ts-rs to `app/src/bindings/SkillInfo`.
- `app/src-tauri/src/skills.rs:45-55,77-80` — `files` counts top-level regular files only.
- `app/src-tauri/src/skills.rs:131-151` — the local branch: `home/.claude/skills/<name>`, `copy_dir_recursive`.
- `app/src-tauri/src/skills.rs:86-104` — the recursive copy. It skips symlinks and does not delete stale files.
- `app/src-tauri/src/skills.rs:153-187` — the remote branch: `pick_handle`, `remote_home`, `collect_files`, `mkdir -p`, then `sftp_upload` per file.
- `app/src-tauri/src/skills.rs:222-258` — `skills_installed` = directory names in `~/.claude/skills/` (local) or `ls -1` of the same path (remote). It reports *any* installed skill, not only ones that came from the registry.

**Confidence:** high.

### Q3

**Answer.** There are two viable mechanisms, and repo precedent favours the first.

**(a) Embed the SKILL.md in the binary with `include_str!`.** This needs no Tauri config change and no build-script change. A file at, for example, `app/src-tauri/resources/skills/ymux-brief/SKILL.md` would be compiled in and written to the registry at startup. The repo already moved its bootstrap payloads from runtime resource lookup to `include_*!` (Phase 62.B). The reason given: resource resolution works for an installed bundle but fails for the standalone debug exe that is copied around without `resources/`. Tests for the zellij files pin the same reasoning: "a runtime read passes on a dev box and fails on a user's machine, while a missing or renamed file here fails the BUILD."

**(b) True Tauri resource.** This needs three changes:
1. Add the path to `bundle.resources` in **both** `app/src-tauri/tauri.conf.json` and `app/src-tauri/tauri.macos.conf.json`. The mac file declares its own, shorter `resources` list, which already leaves out the zellij files the Windows list carries.
2. Resolve the file at runtime with `app.path().resource_dir()` / `app.path().resolve(.., BaseDirectory::Resource)`. Probe both `<resource_dir>/resources/...` and the exe directory, the way `resolve_ymux_cli` and `resolve_zellij_config` do.
3. Handle `None` as a supported state.

`build.rs` needs nothing for a committed text file: its staging check is about the gitignored CLI binary (`vault/moc.md` § Build facts). Array-form resources keep their relative path under `$RESOURCE` (Tauri docs).

**Evidence.**
- `app/src-tauri/tauri.conf.json:35-42` — the current Windows/base `bundle.resources` list (6 entries, including `resources/ymux-zellij.kdl` and `resources/layouts/ymux.kdl`).
- `app/src-tauri/tauri.macos.conf.json` `bundle.resources` — 4 entries (`ymux-cli`, `ymux-linux-x64`, `remote-manifest.json`, `ymux-tmux.conf`). It repeats entries from the base list and leaves out the zellij ones. That suggests the platform file's array replaces the base array rather than appending to it; see Open questions.
- `app/src-tauri/src/remote_bootstrap.rs:17-29` — the Phase 62.B rationale and `include_str!/include_bytes!` of `resources/` files.
- `app/src-tauri/src/lib.rs:15465-15471` — the test comment explaining why embedded beats runtime reads. `include_str!("../resources/ymux-zellij.kdl")`.
- `app/src-tauri/src/lib.rs:15545-15560` — test `bundled_zellij_resources_are_declared_in_tauri_conf`. This is a precedent for pinning a bundle entry with a unit test if option (b) is chosen.
- `app/src-tauri/src/lib.rs:3015-3044` — `resolve_zellij_config`: `resource_dir()` plus the exe directory. The comment notes that on Windows `resource_dir()` is the exe directory, and on macOS it is `Contents/Resources` while the exe sits in `Contents/MacOS`.
- `app/src-tauri/src/local_setup.rs:1510-1525` — `resolve_ymux_cli` probes `r.join("resources").join(NAME)` and `r.join(NAME)`.
- `app/src-tauri/Cargo.toml:52` — `tauri = "=2.10.3"`. The `path().resolve` / `BaseDirectory::Resource` API used in `remote_bootstrap.rs:5` exists in this version.
- https://v2.tauri.app/develop/resources/ (retrieved 2026-10-27):
  - Array form keeps the relative path under `$RESOURCE`; a map form allows choosing the destination.
  - At runtime: `app.path().resolve("lang/de.json", BaseDirectory::Resource)?`.
- `docs/vault/build-glue.md` and the root `CLAUDE.md` "Rebaking"/CI sections — resources under `app/src-tauri/resources/` are hash-staged and pulled in by `include_*!`. A new text file there follows the existing pattern.

**Confidence:** high for the repo facts. Medium for exactly how Tauri 2.10.3 merges the mac file's array, because the official reference page only says "gets merged". Raise it by reading `tauri-utils` config-merge source or by building a mac bundle on CI.

### Q4

**Answer.** Seeding belongs in the `.setup(|app| { … })` closure in `lib.rs`, **after** `settings::load_from_disk()` (lib.rs:12888-12897). Next to the existing one-time migrations is the natural place: the Phase 39.B block starts at lib.rs:12909. Two pieces of existing plumbing give "write once, never clobber":

1. **`MigrationFlags` in `settings.rs`.** This is a struct of `#[serde(default)] bool` has-run flags, persisted in settings.json. The Phase 39 block shows the full pattern: read flag → act → set flag → `settings::save_to_disk_pub`. The flag is set whether or not the action changed anything, "so the migration never re-runs".
2. **An existence check on the target.** Write `registry_dir()/ymux-brief/SKILL.md` only if the `ymux-brief/` directory is absent. Write it atomically (`.tmp` then `rename`) in the spirit of Rule #7.

Each check alone has a gap:
- Existence check only: a user who *deletes* the seeded skill gets it back on every boot.
- Flag only: a user whose settings.json is reset gets their edited copy overwritten.

Combining them — seed only when the flag is false **and** the folder is absent, then set the flag — means the skill is written exactly once and an existing copy is never touched. The trade-off: later improvements to the shipped SKILL.md never reach existing users automatically. Handling that would need a version or hash sidecar (overwrite only when the on-disk hash equals a previously shipped hash). No such mechanism exists in the repo today.

Seeding failures should be logged with `log_warn("APP", …)` and must not block boot, like the other setup steps. `skills.rs:8-9` and `docs/vault/backend-panes.md:237-240` currently say population is out of scope, so both need updating in the same change (Rule #18).

**Evidence.**
- `app/src-tauri/src/lib.rs:12787` — `.setup(|app| {`.
- `app/src-tauri/src/lib.rs:12793` — `config_dir()` is resolved at the start of setup.
- `app/src-tauri/src/lib.rs:12888-12897` — settings load ("or write defaults on first run").
- `app/src-tauri/src/lib.rs:12909-12951` — the Phase 39.B migration: flag check, action, `s.migrations.… = true`, `save_to_disk_pub`, with the comment "do this regardless of `changed` so the migration never re-runs".
- `app/src-tauri/src/settings.rs:1339-1359` — `MigrationFlags` with two `#[serde(default)]` bools. It derives ts-rs, so a new field also regenerates `app/src/bindings/MigrationFlags.ts`.
- `app/src-tauri/crates/ymux-core/src/lib.rs:58-70` — `config_dir()` honours `YMUX_CONFIG_DIR` and uses a per-process temp directory under `cfg(test)`, so a seeding unit test does not touch the real profile.
- `CLAUDE.md` Rule #7 (atomic `.tmp` + rename) and Rule #4 (no `unwrap`) apply to the new writer.

**Confidence:** high for the hook location and the flag mechanism. The deleted-skill / update-propagation policy is a product choice the evidence cannot settle (see Open questions).

### Q5

**Answer.** The SKILL.md must teach exactly what the desktop parser accepts. The Queue empty-state snippet (`BRIEF_SNIPPET`) is the existing canonical agent-facing wording and "must match brief.rs's parser exactly", so the skill body should reuse it verbatim. The skill must teach:

1. End **every** final answer with the block as its last lines, starting with the marker line `[ymux-brief]`.
2. The eight keys: `task`, `status`, `ask`, `rec`, `next`, `delta`, `goal`, `done`.
3. `status` is one of `working | waiting-for-you | stuck | done`.
4. Every value is at most 80 chars, imperative, and on one line.
5. `goal` and `done` are sticky: write them in the first brief, and repeat them only when they change.
6. `ask` never appears without `rec`.
7. Only this turn's facts; leave a field out rather than leaving it empty.

Things the skill does *not* need to teach, because the parser tolerates them:
- case of the marker
- markdown decoration
- the aliases `waiting`, `blocked`, `done-when`
- unknown keys
- the last marker winning, so quoting the format mid-answer is safe
- values in Hebrew or Arabic (keys must stay ASCII)

**Mismatch to flag.** Claude Code loads a skill's full body only when its `description` matches the task ("full skill content only loads when invoked"). The brief, however, must be written on *every* final answer. A model-invoked skill is therefore a weaker always-on carrier than a CLAUDE.md snippet. The description has to be written so the skill is invoked at the start of every session, or the skill body can tell the agent to add the snippet to the project's CLAUDE.md. Whether agents actually emit briefs more reliably via the skill is unmeasured.

**Evidence.**
- `docs/BRIEF.md:11-24` — the wire format and the eight keys.
- `docs/BRIEF.md:26` — "Every value is ≤ 80 chars, imperative, and one line."
- `docs/BRIEF.md:28-32` — sticky `goal` / `done` and the `done` aliases.
- `docs/BRIEF.md:34-43` — parser rules: whole-line case-insensitive marker, last occurrence wins, ASCII keys, decoration stripped, unknown keys ignored, ~200-char clip, status aliases, `ask` needs `rec`.
- `docs/BRIEF.md:45-46` — with no block, the desktop shows a degraded brief.
- `docs/BRIEF.md:60-64` — the Queue empty state is the adoption path; "a bundled skill is BACKLOG".
- `app/src/QueuePanel.tsx:32-54` — `BRIEF_SNIPPET`, the verbatim agent instructions, "must match brief.rs's parser exactly".
- `app/src-tauri/src/brief.rs:51` `FIELD_MAX_CHARS = 200`, `:58` `MARKER`, `:72-78` status aliases.
- `app/src-tauri/src/brief.rs:191-235` — `parse_brief` keys, including `done-when|done_when|done when`.
- `app/src-tauri/src/brief.rs:238-255` — a missing status becomes `Done`.
- https://code.claude.com/docs/en/skills (retrieved 2026-10-27):
  - SKILL.md = YAML frontmatter (`name` optional, defaults to the directory name; `description` recommended, used "to decide when to apply the skill", 1,536-char listing cap) plus a markdown body.
  - Personal skills live at `~/.claude/skills/<name>/SKILL.md`, which matches the `skill_install` destination.
  - "skill descriptions are loaded into context … full skill content only loads when invoked."

**Confidence:** high for the content requirements. Medium for the always-on gap, which is inferred from the docs and not measured.

## Options

| Option | What | Cost | Risk | Evidence |
|---|---|---|---|---|
| A — embed + flag-gated seed | `include_str!` a committed `resources/skills/ymux-brief/SKILL.md`; in `setup()` write it to `registry_dir()/ymux-brief/` when the `MigrationFlags` flag is false **and** the folder is absent; set the flag | ~1 new file, one new `MigrationFlags` field (plus its ts-rs binding), ~20 lines in setup, a unit test, vault page edits | Shipped updates never reach existing users | `remote_bootstrap.rs:17-29`, `lib.rs:12909-12951`, `settings.rs:1339-1359` |
| B — Tauri resource + seed | Same seed, but source read via `resource_dir()` | Two `tauri*.conf.json` edits, a runtime resolver, handling for a missing resource | The standalone debug exe has no `resources/` (the Phase 62.B failure class); the mac list can diverge | `tauri.conf.json:35-42`, `tauri.macos.conf.json`, `lib.rs:3015-3044` |
| C — A plus a hash sidecar | As A, but re-seed when the on-disk SKILL.md hash equals a previously shipped hash | More code: a hash list kept in sync with each release | More moving parts; nothing in the repo does this today | none in repo |

## Recommendation

I recommend Option A: embed the SKILL.md with `include_str!` and seed it once in `setup()`, gated on a new `MigrationFlags` field **and** on `ymux-tools/skills/ymux-brief/` being absent. Embedding follows the repo's own Phase 62.B lesson (`remote_bootstrap.rs:17-26`). It needs no `tauri.conf.json` / `tauri.macos.conf.json` edits and it works for the standalone debug exe. The double gate means a user's edited or deleted copy is never overwritten or resurrected.

The skill body should reuse `BRIEF_SNIPPET` (`QueuePanel.tsx:36-54`) verbatim, with a `description` written so the skill triggers at the start of every session. A shared constant, or a test that asserts the SKILL.md body contains the snippet, would keep the two copies from drifting.

The same change must also:
- update the doc comment at `skills.rs:8-9`
- update `docs/vault/backend-panes.md:237-240`
- remove "(a bundled skill is BACKLOG)" from `docs/BRIEF.md:63-64`

The trade-off accepted is that SKILL.md improvements do not reach users who already have it. What would change this: a requirement that the skill auto-update (then use C), or CI evidence that the mac bundle needs runtime resources anyway (then use B).

## Open questions

- **Q3 (partial):** Does Tauri 2.10.3 replace or concatenate `bundle.resources` when `tauri.macos.conf.json` sets it? The repo layout suggests it replaces, but the official reference page only says "merged". To answer: read the `tauri-utils` config merge source for 2.10.3, or check a mac bundle's `Contents/Resources` from a `build-macos-intel.yml` artifact. This only matters if Option B is chosen.
- **Q4 (policy):** Should a user-deleted `ymux-brief` stay deleted, and should shipped updates overwrite an *unedited* seeded copy? This is a product decision for the owner, not something the evidence settles.
- **Q5 (unmeasured):** Do agents emit `[ymux-brief]` more reliably via a model-invoked skill than via the CLAUDE.md snippet? No measurement exists. To answer: count degraded vs parsed briefs (`PaneBrief.degraded`, `brief.rs`) across sessions with each adoption path. Brief contents are never logged (Rule #1), so this needs a count-only metric.
